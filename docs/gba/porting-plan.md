# GBA porting plan (proposal)

Status: **toolchain chosen (Butano); `gba/game` skeleton exists but is not yet compiled; card pool
defined.** Update this file as decisions are made; record them in
the "Decisions log" at the bottom so later sessions don't re-litigate them.

## Target hardware

| Resource | GBA | Implication |
|---|---|---|
| CPU | ARM7TDMI @ 16.78 MHz, no FPU, no cache | Integer-only, avoid deep recursion and dynamic dispatch in hot loops |
| Fast RAM | 32 KB IWRAM | Hot code (ARM mode) + small hot state |
| Work RAM | 256 KB EWRAM | **Entire game state must fit here** (cards in play, stack, effects) |
| ROM | up to 32 MB cartridge | Card data, art, compiled scripts |
| Save | 32–128 KB SRAM/Flash | Collection, decks, progress |
| Screen | 240×160, tiles + sprites | Very little room for card text; needs zoom/detail views |
| Input | D-pad, A, B, L, R, Start, Select | Every PlayerController decision needs a pad-friendly UI |

Forge's Java engine cannot run here (no JVM, ~1 GB heap typical). So the GBA engine is a
**re-implementation** in C (or C++ without exceptions/RTTI), using Forge as the behavioural spec.

## Proposed architecture

```
forge-gui/res/cardsfolder/*.txt ──► [converter, runs on PC] ──► gba/data/*.c / .bin (packed card DB)
                                            │
                                            └── reports cards it can't compile (unsupported API/keyword)

gba/game/      Butano project: UI screens (board, hand, card zoom, targeting cursor, stack view), art, audio  [exists]
gba/engine/    rules engine in C++, mirrors forge-game structure (phases, stack, SBA, triggers…)    [planned]
gba/ai/        simple heuristic AI, modelled on forge-ai's per-API canPlayAI logic                   [planned]
gba/tests/     engine unit tests that build and run on the PC (host build), compared against Forge   [planned]
gba/cardpool/  card lists + generated feature reports                                                [exists]
gba/tools/     PC-side scripts (card pool report, later the script converter)                        [exists]
```

Everything lives under top-level `gba/`, **not** a Maven module. Keep the Forge Java tree
untouched so upstream merges stay clean. Setup and art workflow: `gba/README.md`.

### Toolchain: Butano (decided)

- **Butano** (C++ on devkitARM): BMP + JSON asset pipeline, sprite/background animation actions,
  automatic VRAM/palette management, sprite-font text. Emulator: **mGBA**.
- Butano style: C++ without exceptions/RTTI, no heap-heavy containers — use `bn::vector<T, N>`
  and other fixed-capacity types.
- **The rules engine must not include Butano headers.** `gba/engine` is plain C++17 using only
  fixed-size arrays and its own small containers, so it also compiles natively on the PC for
  unit tests. The Butano project adds the engine sources via `SOURCES`/`INCLUDES` in
  `gba/game/Makefile`; the UI talks to the engine through a narrow interface (the GBA equivalent
  of Forge's `PlayerController`: "choose target from these", "declare attackers", …).

### Converter (PC side)

Options, roughly in order of fidelity:
1. **Java tool inside this repo** reusing `forge-core`'s `CardRules` parser, emitting C tables.
   Most faithful parsing; adds one small Java class (keep it under `gba/tools/`, not in Forge modules).
2. **Python script** re-parsing the `Key$ Value | ...` format directly. Simpler, easy to iterate.

Either way the output should be a compact bytecode or struct-per-ability form:
`{api_id, params…, target_filter_id, amount_expr_id, sub_ability_index}`, with filters and amount
expressions deduplicated into shared tables. The converter must **refuse** (and list) cards using
anything the GBA engine does not implement, rather than emit partially-working cards.

## Scope: the card pool

The minimum card pool is **`gba/cardpool/maloney_foundations.txt`** (330 distinct cards, 360 entries;
duplicate lines are extra copies). All 330 have Forge scripts.
`gba/cardpool/maloney_foundations_report.md` (generated by `gba/tools/cardpool_report.py`) lists
every feature the pool uses and which cards use it — **that report is the engine's feature
checklist.** The pool has no basic lands; the game will need them added.

Highlights from the report:
- **Not needed at all:** tokens, +1/+1 or other counters, planeswalkers, double-faced/split cards,
  hybrid/phyrexian mana. This keeps the engine much smaller.
- **Core effects (most cards):** Draw, Mana, Pump/PumpAll, ChangeZone, Tap, DealDamage, GainLife,
  Destroy, Discard, Scry, LoseLife, Surveil, Fight, Counter, Mill, Sacrifice, Charm.
- **Keywords:** Flying, Haste, Enchant (Auras), Flash, Trample, Deathtouch, Vigilance, Defender,
  First/Double Strike, Lifelink, Reach, Flashback, Menace, Prowess, Kicker, Equip, Changeling;
  one card each for Hexproof, Ward, Crew, Cascade.
- **Triggers:** ChangesZone (79 cards: ETB/dies/LTB) dominates; then Attacks, Phase, SpellCast,
  AttackersDeclared, LifeGained, and singletons.
- **Statics:** Continuous (anthems, aura/equipment boosts, Control Magic/Confiscate = layer 2
  control change), ReduceCost, CantBlock/CantAttack, MustAttack.
- **Replacements:** Moved = "enters tapped" lands (33 cards); DamageDone doubling on two cards.
- **Hard singletons to schedule late:** Teach by Example (copy spell), Aurelia (extra combat),
  Maelstrom Colossus (cascade), Cultivator's Caravan (crew/vehicles), Herald of Eternal Dawn
  (can't lose), Roughshod Duo (expend), Angrath's Marauders / Twinflame Tyrant (damage doubling),
  Firdoch Core (animate artifact), Mine Collapse (alternative cost), Thriving lands (choose a color
  as it enters).

General engine features regardless of pool:

- Two players only; no multiplayer, Commander, Planechase, Archenemy, Contraptions, Attractions.
- Turn structure, priority, stack, state-based actions, combat incl. first strike / trample.
- Mana: five colors + colorless, generic costs, X.

Suggested order: vanilla creatures + lands + combat → ETB/dies triggers and simple spells →
auras/equipment/anthems (statics) → the hard singletons. Drive the converter's "unsupported"
list to zero for the pool.

### Things that are deliberately simplified versus Forge

Record each simplification here when made, with the Forge code it diverges from:
- Full layer dependency ordering (`GameAction.checkStaticAbilities`) → timestamp order only.
- Undo, network, game views/events, animations hints → not ported.
- AI simulation (`forge-ai/.../simulation`) → not ported; heuristics only.

## Verifying behaviour against Forge

For a rules scenario, write the same setup twice:
1. Java: a test in `forge-gui-desktop/src/test/java/forge/ai/simulation/` style
   (`initAndCreateGame`, `addCard`, `devModeSet`, resolve, assert) — or a `.pzl` puzzle.
2. GBA host build: the same board in `gba/tests/`, asserting the same outcome.

Forge is the oracle: if they disagree, the GBA side is wrong unless the divergence is listed above.

## Legal notes

- Forge is **GPL-3.0**. A C port derived from its logic, and data generated from its scripts,
  should be GPL-3.0 too; keep `LICENSE` and attribution.
- Magic: The Gathering card names, rules text, art and mana symbols belong to Wizards of the Coast.
  Fan projects generally avoid distributing official art; consider original art or text-only cards.
